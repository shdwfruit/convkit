# Defaults calibration (Task 15)

This records real measurements of convkit's six output defaults ("The six
defaults that constitute the product", spec §7), taken on this
development machine (Windows 10). `ffmpeg`/`ffprobe` and `pandoc` are
installed via convkit's own managed install directory
(`%LOCALAPPDATA%\convkit\bin` -- `ffmpeg`/`ffprobe` 9.0.1-essentials,
`pandoc` 3.11), which is what `conv` itself resolves to and what the two
`conv`/`cargo run` invocations below used. The ad hoc `ffmpeg`/`ffprobe`
shell commands in this doc (naive-vs-tuned comparisons, timing runs, VMAF)
instead picked up whatever was first on `PATH`, a separate winget install
of `ffmpeg`/`ffprobe` 9.0-full. Both are the same `gyan.dev` 9.0.x release
train, one version-with-a-patch-release apart, and `-full` vs.
`-essentials` differs only in which optional third-party libraries are
compiled in, not in libx264/libavcodec's own GIF or H.264 encoders --
noted here for reproducibility, not because I expect it to change any
number below. `magick` and `soffice` are **not** installed on this machine
at all, so items 3, 4 (JPEG only), and 5 could not be measured locally;
they are recorded as pending CI verification (Task 16 runs the full
backend matrix on Ubuntu).

Every number below is a real measurement from a command actually run on
this machine on 2026-08-29, not an estimate, and every command is given in
full -- no `...` placeholders -- so a third party can rerun any of them.
The one tool built specifically for this calibration (the GIF colour
counter, §2) is committed at
`crates/convkit-core/examples/count_colors.rs` rather than being a
throwaway script, so its frame-stride handling, byte alignment, and EOF
behaviour are auditable, not just its output.

**Headline result: one spec claim is contradicted by measurement** -- the
"~100x faster" auto-remux figure (§1). No numeric code default (CRF,
quality, fps, width) needed to change; §2 and §4 found real, interesting
effects but not ones a single non-representative fixture justifies acting
on. Details and reasoning in each section.

Test fixture used throughout: `tests/fixtures/clip.mp4`, a 2-second
640x360 H.264/AAC clip generated by

```
ffmpeg -f lavfi -i testsrc=size=640x360:rate=30:duration=2 \
       -f lavfi -i sine=frequency=440:duration=2 \
       -c:v libx264 -crf 20 -pix_fmt yuv420p -c:a aac -b:a 160k \
       tests/fixtures/clip.mp4
```

(56,325 bytes.) `testsrc`/`sine` are ffmpeg's synthetic test generators: a
moving colour-bar/gradient pattern and a pure sine tone. This matters for
the caveats below -- synthetic content has no sensor noise or natural
detail, which is exactly where some of these defaults (CRF, palette
dithering) are supposed to matter most.

## 1. Auto-remux (spec §7.1)

**Spec claim (`docs/superpowers/specs/2026-08-29-convkit-design.md:231`):**
"roughly 100x faster" than transcoding, when the source codecs already fit
the target container (`plan::select` picks `REMUX_MP4`/`REMUX_WEBM`, a
`-c copy` stream copy, over `VIDEO_TO_MP4`'s full transcode).

**Method:** for each of three clip sizes, generated a synthetic source
with `ffmpeg -f lavfi`, remuxed it to MKV with `-c copy` to get test
input, then timed convkit's exact remux argv (`REMUX_MP4` in
`registry.rs`) and exact transcode argv (`VIDEO_TO_MP4`) run directly
against that MKV, wall-clock via `date +%s%N`, 5-7 runs each, averaged.
Repeated at three sizes to see how the ratio scales, since a 2-second clip
clearly wasn't going to be a fair test of a "100x" claim by itself, and
every row below is a multi-run average with the raw samples shown -- none
of this table rests on a single measurement.

**Row 1: the committed fixture (2s, 640x360, `tests/fixtures/clip.mp4`,
generated by the command at the top of this doc).**

Remux argv timed: `ffmpeg -y -i clip.mkv -c copy -sn -movflags +faststart out.mp4`
Transcode argv timed: `ffmpeg -y -i clip.mkv -c:v libx264 -crf 20 -preset medium -pix_fmt yuv420p -c:a aac -b:a 160k -sn -movflags +faststart out.mp4`

```
remux (7 runs):      68, 63, 63, 67, 63, 63, 64 ms   (avg 64)
transcode (7 runs): 211, 209, 209, 211, 213, 212, 209 ms  (avg 210)
```

**Row 2: 30s, 1280x720.** Source generated with:

```
ffmpeg -f lavfi -i testsrc=size=1280x720:rate=30:duration=30 \
       -f lavfi -i sine=frequency=440:duration=30 \
       -c:v libx264 -crf 20 -pix_fmt yuv420p -c:a aac -b:a 160k \
       clip30_720.mp4
ffmpeg -i clip30_720.mp4 -c copy clip30_720.mkv
```

Remux argv timed: `ffmpeg -y -i clip30_720.mkv -c copy -sn -movflags +faststart out.mp4`
Transcode argv timed: `ffmpeg -y -i clip30_720.mkv -c:v libx264 -crf 20 -preset medium -pix_fmt yuv420p -c:a aac -b:a 160k -sn -movflags +faststart out.mp4`

```
remux (5 runs):      103, 85, 89, 78, 95 ms      (avg 90)
transcode (5 runs): 2380, 2351, 2339, 2379, 2348 ms  (avg 2,359)
```

**Row 3: 60s, 1920x1080.** Source generated with:

```
ffmpeg -f lavfi -i testsrc=size=1920x1080:rate=30:duration=60 \
       -f lavfi -i sine=frequency=440:duration=60 \
       -c:v libx264 -crf 20 -pix_fmt yuv420p -c:a aac -b:a 160k \
       clip60_1080.mp4
ffmpeg -i clip60_1080.mp4 -c copy clip60_1080.mkv
```

Remux argv timed: `ffmpeg -y -i clip60_1080.mkv -c copy -sn -movflags +faststart out.mp4`
Transcode argv timed: `ffmpeg -y -i clip60_1080.mkv -c:v libx264 -crf 20 -preset medium -pix_fmt yuv420p -c:a aac -b:a 160k -sn -movflags +faststart out.mp4`

```
remux (5 runs):      137, 154, 144, 120, 109 ms   (avg 133)
transcode (5 runs): 9526, 9531, 9531, 9480, 9529 ms  (avg 9,519)
```

*(An earlier pass through this measurement, before this doc's own
reproducibility bar was applied to it, ran this row's transcode only once
-- 9,511 ms, close to but not this table's 9,519 ms average -- and
reported this row's multiplier as 64.3x from that single run. That figure
has been superseded by the 5-run measurement above and is not used
anywhere else in this doc; it's noted here only so nobody re-derives it
from an old copy and wonders why it doesn't match.)*

**Summary table:**

| clip | remux avg | transcode avg | runs (each) | **measured multiplier** |
|---|---|---|---|---|
| 2s, 640x360 (committed fixture) | 64 ms | 210 ms | 7 | **3.3x** |
| 30s, 1280x720 | 90 ms | 2,359 ms | 5 | **26.2x** |
| 60s, 1920x1080 | 133 ms | 9,519 ms | 5 | **71.7x** |

**Verdict: the spec's "~100x" claim is CONTRADICTED for the committed
fixture and for realistic short clips generally.** On the actual 2-second
fixture, remuxing is **3.3x** faster, not 100x -- the ~60ms floor is
almost entirely fixed ffmpeg process-startup and demux overhead, not work
that scales away. The multiplier climbs steeply with clip length and
resolution (3.3x -> 26.2x -> 71.7x as size grows), which is exactly what
you'd expect: transcode cost scales with total pixels, remux cost does
not. Extrapolating that trend, 100x is plausible on a multi-minute or 4K
source, but that is not what most users convert most of the time, and it
is not what the fixture demonstrates.

There is no numeric code default to change here -- `-c copy` is already
the fastest possible ffmpeg invocation; there's no dial to turn. What's
wrong is the documentation claim itself. **I have not edited
`docs/superpowers/specs/2026-08-29-convkit-design.md`** (Task 15's file
list is `tests/`, `docs/defaults-calibration.md`, and the test crate; the
design spec is a planning artifact I was told not to read in full, not a
listed output of this task) -- the controller has confirmed they are
correcting the spec on the strength of this finding separately. Suggested
replacement language: *"a stream copy instead of a re-encode -- an order
of magnitude or more faster for typical clips, and dramatically more for
longer or higher-resolution ones, measured at 3-26x on clips from 2 to 30
seconds and up to 72x on a 1080p/60s clip."*

The property test `mkv_to_mp4_with_compatible_codecs_is_a_stream_copy`
(§7) asserts the *mechanism* (`outcome.remuxed == true`, output codec
unchanged), not any particular speedup number -- that assertion holds
regardless of this finding and passed for real on this machine.

## 2. GIF via generated palette (spec §7.2)

**Recipe:** `TO_GIF` in `registry.rs` -- `fps=15,scale=w=min(640\,iw):h=-2`
into a two-pass `palettegen=stats_mode=diff` / `paletteuse=dither=bayer`
filtergraph, vs. the brief's naive comparison command.

**Commands:**

```
ffmpeg -i tests/fixtures/clip.mp4 naive.gif
conv tests/fixtures/clip.mp4 tuned.gif      # built from this branch, release profile
```

**`magick identify` was not available to measure colour count** (`magick`
is not installed on this machine -- see the standing constraints). Per the
brief, I measured what I could without it: `ffprobe` for frame/size/rate
properties, and a real, exact colour-count analysis built from ffmpeg's
own raw frame output. ffmpeg can decode either GIF to a raw RGB24 dump:

```
ffmpeg -i naive.gif -f rawvideo -pix_fmt rgb24 naive_all.raw
ffmpeg -i tuned.gif -f rawvideo -pix_fmt rgb24 tuned_all.raw
```

and (for a first-frame-only figure alongside the whole-clip one)

```
ffmpeg -i naive.gif -frames:v 1 -f rawvideo -pix_fmt rgb24 naive_f0.raw
ffmpeg -i tuned.gif -frames:v 1 -f rawvideo -pix_fmt rgb24 tuned_f0.raw
```

That raw dump is then counted by a small, **committed** Rust tool --
`crates/convkit-core/examples/count_colors.rs` -- run with:

```
cargo run -p convkit-core --example count_colors -- naive_all.raw
cargo run -p convkit-core --example count_colors -- tuned_all.raw
```

It counts exact distinct RGB24 triplets via a 2 MiB seen-bitset over the
full 2^24 RGB space (one bit per possible colour, indexed by
`(r<<16)|(g<<8)|b`) -- exhaustive and exact, not a sample or a hash
estimate. It was committed specifically so this number is auditable and
re-runnable rather than resting on a deleted script; re-running the whole
pipeline above against freshly-generated GIFs while preparing this
revision reproduced the identical figures below (463,337 / 539,921 byte
GIFs, 170 / 248 / 153 / 231 colours) exactly.

**Measured (via `ffprobe -show_entries stream=width,height,nb_frames,
avg_frame_rate` and file size):**

| | naive `ffmpeg -i clip.mp4 out.gif` | tuned (convkit) | delta |
|---|---|---|---|
| file size | 463,337 B | 539,921 B | **+16.5%** |
| dimensions | 640x360 | 640x360 | same |
| frame count | 60 | 30 | -50% (15fps cap working) |
| avg frame rate (ffprobe) | 100/3 (~33.3fps -- GIF's centisecond-granularity delay field quantizing the 30fps source) | 50/3 (~16.7fps -- same quantization on the 15fps target) | fps cap confirmed applied |

**Measured (via `count_colors`):**

| | naive | tuned | delta |
|---|---|---|---|
| unique colours, frame 0 | 153 | **231** | **+51%** |
| unique colours, all frames combined | 170 | **248** | **+46%** |

**Verdict on palette quality: CONFIRMED, strongly.** The custom
`stats_mode=diff` palette plus Bayer dithering realizes far more of the
256-colour GIF palette budget than ffmpeg's own default GIF encoder does
on this content (231 vs. 153 distinct colours on frame 0 -- both safely
above the property test's `> 64` threshold, but the tuned recipe is using
50%+ more of the available palette). This is a real, meaningful
improvement in colour fidelity, exactly as the spec intended.

**Verdict on file size: a genuine, measured caveat, not a default
change.** The tuned output ended up **16.5% larger** than the naive one
on this fixture, despite having half as many frames -- the richer
per-frame palette and ordered dithering cost more bytes per frame (about
2.3x: ~18.0 KB/frame tuned vs. ~7.7 KB/frame naive) than halving the frame
rate saves. I am not recommending a change to the 15fps/640px caps over
this: `testsrc` is a constantly-moving, high-frequency synthetic pattern
with no flat regions at all, which is close to worst-case content for
palette+dithering-based GIF compression, and it's also far too small
(640x360, 2s) to exercise the caps' actual purpose, which is bounding
worst-case output size on *longer or higher-resolution* real source video
(the caps can't reduce size below the naive command's on a clip already
under both limits -- there's nothing for them to cap). **Recommendation:**
re-run this same naive-vs-tuned comparison against representative
real-world footage (a screen recording or handheld phone clip, which is
what GIF conversion is mostly used for) in Task 16 CI or a follow-up,
where the frame-rate/width caps have room to actually bind.

## 4. Quality anchors (spec §7.4): CRF 20 / AAC 160k, and JPEG quality 92

Spec §7.4 bundles two anchors under one item; measured status differs
between them.

### CRF 20 / AAC 160k -- measured

**Recipe:** `VIDEO_TO_MP4` in `crates/convkit-core/src/registry.rs` --
`-c:v libx264 -crf 20 ... -c:a aac -b:a 160k`.

**Command compared against:** the same synthetic source encoded with
ffmpeg's own untouched defaults (no `-crf`, no `-b:a` -- libx264 defaults
to CRF 23, ffmpeg's native AAC encoder picks its own bitrate):

```
ffmpeg -f lavfi -i testsrc=size=640x360:rate=30:duration=2 \
       -f lavfi -i sine=frequency=440:duration=2 \
       -c:v libx264 -pix_fmt yuv420p -c:a aac \
       naive_defaults.mp4
```

**Measured (via `ffprobe -show_entries format=size,bit_rate -show_entries
stream=codec_name,bit_rate`):**

| | `clip.mp4` (CRF 20 / AAC 160k) | naive (CRF 23 / AAC default) | delta |
|---|---|---|---|
| file size | 56,325 B | 36,942 B | **+52.4%** |
| video bitrate | 75,088 bps | 62,880 bps | +19.4% |
| audio bitrate | 134,269 bps | 69,694 bps | +92.7% |
| codec | h264 / aac | h264 / aac | same |

**Perceptual quality (bonus measurement):** this ffmpeg build has
`--enable-libvmaf`, so I could go beyond file size and measure actual
perceptual quality via VMAF against a lossless reference of the same
synthetic source. Full command, both parameters matched to the 2s/640x360
encode so frame count and resolution align between reference and
distorted input:

```
ffmpeg -i clip.mp4 -f lavfi -i "testsrc=size=640x360:rate=30:duration=2" -lavfi "[0:v][1:v]libvmaf" -f null -
```

`libvmaf` writes its result -- `[Parsed_libvmaf_0 @ ...] VMAF score:
97.297290` -- as an ffmpeg log line to **stderr**, at `-loglevel info` or
quieter default (not `error`), not to stdout, so capturing it needs either
`2>&1` before any pipe/grep or `-loglevel info` explicitly, e.g.:

```
ffmpeg -i clip.mp4 -f lavfi -i "testsrc=size=640x360:rate=30:duration=2" -lavfi "[0:v][1:v]libvmaf" -f null - 2>&1 | grep -i vmaf
```

Run against both the CRF20 encode and the naive CRF23-default one (same
command, `naive_defaults.mp4` in place of `clip.mp4`):

| | VMAF score |
|---|---|
| CRF 20 (`clip.mp4`) | **97.30** |
| CRF 23 (naive default) | 97.02 |

**Verdict: keep CRF 20 / AAC 160k, but the measurement is inconclusive on
this fixture, not confirming.** The 52% size premium is real and
measured. But the VMAF delta between CRF 20 and ffmpeg's own CRF 23
default is only 0.28 points, and both land comfortably in the
"visually-transparent" band (VMAF > 95). `testsrc` is synthetic:
noise-free gradients and colour bars are close to the easiest possible
content for an encoder, and CRF differences are most visible exactly on
the natural sensor noise this fixture doesn't have. I am not treating a
0.28-point VMAF gap on adversarially-easy content as grounds to change a
quality anchor the spec set for real-world (phone/camera) footage --
that would be overfitting the default to the one fixture I happened to
generate. **Recommendation for Task 16 or a follow-up:** re-run this same
VMAF comparison against a real handheld/phone clip (with natural grain)
before drawing a conclusion either way; if CRF 20 still buys negligible
VMAF over CRF 23 on real footage, that would be a real reason to
reconsider the anchor.

### JPEG quality 92 -- pending CI verification

## 5. PDF -> DOCX honesty (spec §7.5)

Spec §7.5 is specifically about the *fidelity warning* on this
conversion, not just the conversion itself: "attach a `fidelity` warning
... stating that PDF carries no paragraph structure to recover ... a
value returned by core, rendered once as a note by the CLI frontend and
carried as a `warnings` array under `--json`."

**What is structurally verified (already part of the 133-test baseline,
not new to this task):**

- The recipe actually declares the warning:
  `PDF_TO_DOCX` in `registry.rs` sets
  `warnings: &["PDF stores positioned glyphs, not paragraphs, so the
  result is a set of text boxes rather than a flowing document. Expect to
  reflow it by hand."]`, verified by
  `registry::tests::pdf_to_docx_names_the_word_filter_and_warns_about_fidelity`
  (asserts exactly one warning, containing "text boxes").
- The warning survives into a built plan:
  `plan::tests::warnings_travel_on_the_plan` builds a real `pdf -> docx`
  plan and asserts `plan.warnings.len() == 1`.
- The rendering mechanism the spec describes is implemented generically
  (not specific to this pair, but this pair is exactly what exercises
  it): `crates/conv/src/render.rs`'s `outcome_human` prints `note: {w}`
  for every warning in `Outcome::warnings`, and `outcome_json` includes
  `"warnings": o.warnings` verbatim in the `--json` envelope. There is no
  separate code path for "the pdf-to-docx warning" specifically -- it's
  the same `Outcome::warnings` plumbing every recipe's warnings go
  through (see also `TO_GIF`'s and `VIDEO_TO_MP4`'s warnings, exercised
  the same way).

**What is NOT measured here, pending Task 16 CI:** an actual `soffice`
run converting a real PDF to DOCX, and confirming by hand that the result
genuinely is positioned text boxes (i.e. that the warning describes real
behaviour, not just that the string exists). `soffice` is not installed
on this machine. `docx_to_pdf_produces_a_real_pdf` (§7) exercises the
*other* direction (`docx -> pdf`, needed because `sample.docx`, not a PDF,
is the fixture on hand) and fails the same way -- `backend_missing:
soffice`.

## 6. Atomic output (spec §7.6)

**Not a numeric default -- a behavioural guarantee, and not something
this task measures with a command.** Spec §7.6: "Temp file plus rename,
plus stat-ing the result," pointing at §5.5's execution invariants: write
to a temp file in the destination directory then atomically rename;
always `stat` the result and treat a missing or zero-byte output as
failure regardless of exit code; give every `soffice` invocation an
isolated profile.

This is implemented in `crates/convkit-core/src/exec.rs`'s `run()`, and
is already covered by existing tests in that file (part of the 133-test
baseline, not new to this task):

- `a_successful_step_renames_into_place_and_reports_size` -- the
  temp-file-then-rename path itself.
- `no_temp_files_survive_a_successful_run` -- no scratch/temp artefacts
  left behind after a clean run.
- `a_backend_that_writes_nothing_is_a_failure_even_on_exit_zero` -- the
  "stat and treat zero-byte as failure regardless of exit code" invariant
  explicitly named in spec §5.5 (load-bearing for `soffice`, which exits 0
  on failure).
- `outdir_recipe_never_touches_a_decoy_already_in_the_destination_directory`
  -- the scratch directory (not the user's real destination) is what
  `soffice --outdir` ever sees, so a pre-existing same-named file in the
  destination can never be mistaken for freshly-produced output. This is
  the fix for a real data-loss bug found during an earlier task's review
  (see that test's own doc comment in `exec.rs`), which is exactly the
  failure mode "atomic output" as a product default exists to prevent.
- `a_mid_recipe_failure_leaves_no_scratch_directory_behind` -- a failure
  partway through a multi-step recipe (e.g. `md -> pdf`'s pandoc-then-
  soffice) still cleans up completely, including whatever the earlier,
  successful step already wrote.
- `scratch_guard_removes_a_populated_directory_on_drop` -- cleanup is
  unconditional (`Drop`-based), not dependent on reaching a particular
  return statement, proven against a populated directory mirroring a real
  LibreOffice profile.

I considered whether there's a real-backend measurement analogous to the
other five items (e.g. `kill -9` a real conversion mid-flight and confirm
no truncated file lands at the destination) and decided against adding
one for this task: the guarantee is about `exec::run`'s own control flow
(the `ScratchGuard` `Drop` impl, the rename-not-write-in-place ordering),
which the existing unit tests already exercise directly and
deterministically, including failure injection that would be awkward to
reproduce reliably by actually killing a live backend process. A `kill
-9`-based end-to-end test would be a reasonable addition to the suite,
but it exercises the same code path these six already cover, not a gap
this task's real-backend measurements would close.

## Fixtures

| file | how it was generated | size |
|---|---|---|
| `tests/fixtures/clip.mp4` | the brief's exact `ffmpeg -f lavfi` command (top of this doc) | 56,325 B |
| `tests/fixtures/sample.md` | hand-written | 726 B |

**HEIC fixture: genuinely could not be produced on this machine, and was
not faked.** This machine's ffmpeg 9.0.x builds (both the managed
9.0.1-essentials one convkit itself resolves to, and the PATH 9.0-full
one) have no HEIC/HEIF encoder, muxer, or demuxer at all -- confirmed
directly against both:

```
$ ffmpeg -muxers 2>&1 | grep -i hei      # no output
$ ffmpeg -demuxers 2>&1 | grep -i hei    # no output
$ ffmpeg -i sample.png -c:v libx265 sample.heic
[...] Unable to choose an output format for 'sample.heic'; use a standard
extension for the filename or specify the format manually.
```

## Colour-counting tool

`crates/convkit-core/examples/count_colors.rs`, used in §2. Run with
`cargo run -p convkit-core --example count_colors -- <raw-rgb24-file>`.
Takes a raw `rgb24` frame dump (`ffmpeg -i x.gif -f rawvideo -pix_fmt
rgb24 x.raw`) and prints the exact number of distinct RGB24 colours in it,
via an exhaustive 2 MiB bitset over the full 24-bit colour space. Full
usage and method notes are in the file's own doc comment. Committed (not
a deleted throwaway script) so the §2 findings are independently
re-runnable and auditable, not just their output.
